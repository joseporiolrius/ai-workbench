# Session 03 — Version Control at Team Scale + Continuous Integration

Session 03 solves the problem of scaling Git and quality control from a solo student to a team: it introduces branch protection, pull requests, peer review, and a student-authored GitHub Actions CI workflow as the required merge gate. Working in pairs on their own `hello-world` repositories, students feel a protected-branch rejection, get a bad commit message rejected by Commitizen, and end the session with a CI workflow (ruff, pytest, commit-message validation) that is green and required before merge.

## Conway's law and review as an institution

The boardroom segment opens with Conway's 1968 observation that organizations design systems that mirror their communication structures — three engineers can share a brain, but thirty engineers ship whatever their process allows through. Google's code review culture is cited as evidence review does not slow throughput: essentially every change is reviewed before merge across tens of thousands of engineers, with median turnaround for small changes measured in hours. A SmartBear/Cisco study of roughly 2,500 reviews found that reviewing 200–400 lines at a time catches most defects, and a defect caught in review costs a fraction of one caught in production. The 2026 framing: when AI assistants write a growing share of code, review becomes the only human control point left — reviewing code you did not write is the core skill of an AI-era professional, practiced today on a partner's code and from now on on an assistant's code.

## The five things to know cold

A branch isolates work; a pull request (PR) is the request to merge that branch into `main`, carrying the diff, discussion, and checks — on a protected branch, merging without a PR is impossible. Branch protection enforces server-side rules: no direct pushes to `main`, at least N approving reviews, and required status checks green; Git hooks are local and bypassable with `--no-verify`, but branch protection is the institution that cannot be bypassed by the author (whether it also binds repo admins is the separate "Include administrators" switch). Conventional commit format remains `type(scope): summary` with common types `feat`, `fix`, `docs`, `test`, `ci`, `chore` — machine-readable history later enables automated changelogs and semantic versioning in Session 5. A workflow file in `.github/workflows/` declares triggers (`on:`), jobs that run on a runner such as `ubuntu-latest` (a fresh, empty VM), and steps such as `actions/checkout` or shell commands — the runner starts with no code checked out. CI means every change is automatically built and tested before merge, with red blocking merge; CI validates the change while CD (Session 5) delivers the validated artifact — a green check that ran zero tests is worse than a red one.

## Branch protection and the peer-reviewed PR

After importing the `starter-s03-v1.0.0` increment (locked dev dependencies, hooks, `scripts/check-commits.sh`, but not the workflow itself), each student adds their partner as a collaborator and enables branch protection on `main`: require a pull request before merging, require one approval, and — critically — enable "Include administrators" ("Do not allow bypassing the above settings" in current GitHub UI), since without it GitHub waves repo admins through and the rejection drill would silently succeed. Students create a feature branch (`feat/greeting-name`), add a `greet(name)` function and test, verify locally with `uv run pytest`, push, and open a PR against their own `main` (template-instantiated, not a fork, so GitHub offers no course-template base). Each partner reviews the other's PR with a minimum bar of one genuine question and one concrete change request, submitting "Request changes," then approving after a fix commit and merging. The direct-push rejection drill proves the guardrail: a push straight to `main` is rejected with GH006/GH013 even though the student is the repo's own admin — screenshotted as evidence.

## Commitizen and the CI workflow

Part B enables local hooks (`git config core.hooksPath .githooks`) so `.githooks/commit-msg` (running `uv run cz check --commit-msg-file "$1"`) rejects a deliberately bad message like `"changed stuff"`, fixed with a proper conventional message — surfacing that hooks are local and skippable with `--no-verify`, so only a server-side check truly enforces the rule at team scale. Part C has students write `.github/workflows/ci.yml` themselves (AI-assisted and expected, but every line must be defensible in a spot-check): name `CI`, triggers `pull_request` and `push` to `main`, one job `quality` on `ubuntu-latest` that checks out full history (`fetch-depth: 0`), installs the pinned `uv` version, runs `uv sync --locked`, `uv run ruff check .`, `uv run pytest`, and `./scripts/check-commits.sh` — uv only, never pip or `requirements.txt`. Once green and merged, the student edits branch protection to require the `quality` status check before merging — an unbypassable second gate alongside review. Students then disable "Include administrators" again, since Session 5's release automation (`cz bump` plus a direct push of `main` and tags) needs an admin bypass a solo owner can grant without undermining the institution for regular feature work.

## Common failure modes and diagnosis

The classic AI-generated mistake is a workflow using `actions/setup-python` plus `pip install -r requirements.txt` when no `requirements.txt` exists in a uv-only course (an immediate red build), pinned stale action versions like `actions/checkout@v2`, or — worst — a deceptively green run where dev dependencies are never installed and pytest reports "collected 0 items" with `|| true` masking the exit code. Instructors show one such log in the debrief and have students find the tell: "1 passed" versus "collected 0 items." This is a named exam skill: a fault-injected `ci.yml` (checkout removed, or `uv run pytest || true`) is a practical exam variant, graded on the fix and the stated reasoning.

## Server-side enforcement and the deliverable

Before merging the CI PR, students make one test commit bypassing the local hook with `--no-verify -m "changed stuff"` and confirm the required `quality` job fails on the bad message — proving enforcement lives on GitHub's server — then amend to a proper conventional message and force-push with `--force-with-lease` to see green. Deliverables are the two merged PRs (feature and CI) with visible review threads, `ci.yml` green on `main`, the `quality` check marked required, `evidence/s03/` populated (branch-protection screenshot, direct-push rejection screenshot, `commitlint-rejection.txt`, green-run screenshot), and a `JOURNAL.md` entry. Oral spot-checks probe the student's own `ci.yml`: what triggers it, why `actions/checkout` must run first when the runner starts empty, what the reviewer changed, and whether deleting `uv run pytest` would still leave the pipeline green — testing whether the student understands what the green checkmark is actually worth.
