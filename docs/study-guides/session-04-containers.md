# Session 04 — Containers: Build Once, Run Anywhere

Session 04 solves the "works on my machine" problem by packaging `hello-world` into a standardized, portable artifact: a container image built from a student-written, cache-friendly, non-root Dockerfile. The technical peak is booting the course's `ai-workbench` Compose stack (pi-web-ui plus Qdrant, images pulled from the course GHCR) on the student's own VM with `docker compose up -d`, then having a first chat with the private AI workbench through an SSH tunnel. Docker and Compose are the only new tools this week; registries and pushing images are deferred to Session 5.

## The shipping-container economics lesson

The boardroom segment retells Malcom McLean's 1956 container-ship story: loading loose cargo cost about $5.86/ton versus roughly $0.16/ton containerized — a nearly 97% cost reduction driven not by the steel box but by the standard interface it created for any crane, ship, or truck. Docker (2013) is framed as the same move for software: one standard artifact runs identically on a laptop, a VM, and a cluster, so "works on my machine" stops being an excuse because the machine ships with the app. Containers start in milliseconds versus minutes for VMs, images run MBs to GBs versus full OS disks, and a single host can run dozens of isolated services — explaining why containers underpin the 2010s' DORA deployment-frequency gains.

## The five things to know cold

An image is an immutable, layered filesystem template — the blueprint — while a container is a running instance with its own writable layer and process; one image can run many containers. Every Dockerfile instruction creates a layer, and changing a file invalidates the first layer that copies it and every layer after it — so dependency manifests must be copied and installed before source code, letting source-only edits reuse the cached dependency layer. Containers share the host kernel and isolate processes, filesystem, and network via namespaces and cgroups (ms startup, MB overhead, weaker isolation); VMs boot a full OS on virtual hardware (minutes, GBs, stronger isolation). Containers must never run as root — `USER appuser` is the norm, since a compromised process without root has a far smaller blast radius. Compose is declarative: `compose.yml` declares services, images, ports, environment, volumes, and dependencies, and `docker compose up -d` idempotently reconciles reality to that declaration; data in named volumes survives `down`, while `down -v` destroys it.

## Writing the Dockerfile and the cache-ordering drill

Students first write a `.dockerignore` excluding `.git`, `.venv`, `__pycache__`, and `evidence/`, since the VM already has a `.venv/` from Session 2 that would otherwise poison the build. The Dockerfile is built on `ghcr.io/astral-sh/uv:python3.12-bookworm-slim`, copies only `pyproject.toml` and `uv.lock` first and runs `uv sync --locked --no-install-project --no-dev` before copying the rest of the source, creates a non-root `appuser` via `USER appuser`, and runs `CMD ["uv", "run", "--no-sync", "hello-world"]` (`--no-sync` because the environment is already built and the container should not touch the network at runtime). The break/fix drill times a correct rebuild after a source edit (roughly 2–5 seconds, dependency layers `CACHED`), then collapses the Dockerfile into the AI-favored naive shape — one early `COPY . .` before a combined `RUN uv sync` — where a subsequent source edit now reinstalls every dependency (60+ seconds). Restoring the correct order confirms the fix; the three timings and reasoning go into `JOURNAL.md`. The Dockerfile and `.dockerignore` are committed through the same PR-and-CI flow from Session 3, since CI still only runs ruff and pytest — image builds join the pipeline in Session 5.

## Booting the AI workbench

The `ai-workbench` repository (private, template-instantiated, like `hello-world`) ships a `compose.yml` with two services: `qdrant` (pinned course GHCR mirror, bound to `127.0.0.1:6333`, data in named volume `qdrant-data`, TCP healthcheck) and `pi-web-ui` (pinned course fork, bound to `127.0.0.1:8787`, reading `.env` for the single `COURSE_VIRTUAL_KEY`, mounting `pi-config/models.json` read-only). The compose file contains no LLM gateway of its own — the professor operates one central gateway for the whole course, and the student's stack consumes it like any SaaS API, an explicit "consume vs operate" lesson; `models.json` points `baseUrl` at the course gateway and `apiKey` at `$COURSE_VIRTUAL_KEY`. After filling `.env` with the personal course virtual key from eCampus, `docker compose up -d` pulls the two pinned images and `docker compose ps` should show both healthy. Because every port is bound to loopback on purpose — pi-web-ui has no authentication and its agent can run shell commands, so exposing it would be remote-code-execution-as-a-service — students reach the UI only through an SSH tunnel (`ssh -i dbai.pem -L 8787:127.0.0.1:8787 ubuntu@<VM_IP>`) until Session 9's "make it private" milestone; until then, the tunnel is the entire security model.

## Exploring the stack and common failure modes

Students trace the one-hop key story — browser to pi-web-ui to the course gateway using `COURSE_VIRTUAL_KEY`, no raw provider key ever touching the student — by tailing `docker compose logs -f pi-web-ui` while chatting. `curl -s http://127.0.0.1:6333/collections` returns an empty list: the workbench's vector database, sitting empty until Session 10's monitoring fixture and Session 12's ingestion of the course study guides. The named classic AI-generated Dockerfile mistake is `FROM python:3.12` with `pip install -r requirements.txt`, an early `COPY . .`, and no `USER` line — plausible, working, but root-running, cache-hostile, and pip-based in a uv-only course; a runner-up is deprecated `docker-compose` (v1) syntax or believing `EXPOSE` publishes a port (it is metadata only; publishing needs `-p`/`ports:`). The exam-variant "silent workbench" renames `COURSE_VIRTUAL_KEY` in `.env` so pi-web-ui's gateway calls fail with 401 even though both containers show healthy — proving "containers healthy" does not mean "system working" when the LLM is a consumed external service; diagnosis needs `docker compose logs` plus a manual gateway `curl` with the key.

## Evidence, deliverables, and what comes next

Evidence in `ai-workbench`'s `evidence/s04/` includes `docker compose ps` showing both services healthy, a screenshot of the first chat, and the Qdrant curl output — `.env` must never be committed. The hello-world deliverable is the merged Dockerfile PR with green CI; homework adds two containers from the same image on different ports (one image, many containers), a minimal `compose.yml` in `hello-world` itself (Session 5's pipeline swaps `build:` for a registry `image:`), a `docker history` inspection of the largest layers, and a persistence drill confirming `down` then `up -d` loses no Qdrant data. As every session, cost discipline requires stopping the EC2 instance and screenshotting the stopped state.
